Why teams use Kasumi

For systems where a retry, a restart, or a replica failure must not become duplicate or ambiguous state.

Store JSON documents, validate them with schemas, query them through typed indexes or English and Japanese full-text search, and commit related changes as one durable operation.

  • 01

    Retries are part of the model

    Every mutation has an idempotency key and a durable receipt. Resend the same batch after an uncertain network outcome and Kasumi resolves the original operation instead of applying it twice.

    • Idempotency keys
    • Durable receipts
  • 02

    JSON without fuzzy semantics

    JSON Schema, exact numeric values, JSON Pointer field paths, conditional writes, aggregates, cursor paging, and declared indexes keep application behavior predictable as data grows.

    • JSON Schema
    • Exact numbers
    • Declared indexes
  • 03

    One atomic boundary for a workflow

    Update an order, reserve inventory, and clear a cart in one batch. Preconditions and read assertions reject the whole batch when the state you observed is no longer true.

  • 04

    Isolation you can operate

    Tenants have separate policy, credentials, encrypted storage, audit records, and, in replicated mode, Raft groups. Network access uses TLS 1.3, mTLS, pinned server certificates, and bearer credentials.

  • 05

    A useful interface for people and agents

    Use the Rust SDK for services, kasumictl for scripts and debugging, native Protobuf for other languages, or MCP for an authorized agent workflow.

The retry model

Send it again. It still applies once.

If the connection drops after dispatch, resend the same batch or let Kasumi::mutate resolve it. The stable key prevents a second application.

Every precondition is checked against one write state. A failed version check, schema validation, uniqueness constraint, quota, or authorization check rejects the entire batch.

Querying

One typed query shape for Rust, gRPC, and MCP.

Field paths are JSON Pointers. Filter, sort, select, page, aggregate, and search with the same JSON from every interface.

  • Declared indexes

    Filtering, sorting, or grouping on a hot path uses an index you declared. Index fields keep their type: numbers compare as exact JSON numbers and nothing is coerced.

  • INDEX_REQUIRED

    A query on an undeclared field returns INDEX_REQUIRED unless the request explicitly opts into a bounded scan. Slow paths are a decision, not a surprise.

  • Seek paging

    For large ordered walks, seek paging reads each page straight from a unique index and keeps no server-side cursor.

  • English and Japanese full-text search

    Declare a text index and choose its analyzer, including English stemming and Japanese morphological analysis. Search combines with filters, sorting, paging, and named aggregates.

Deployment modes

The same policy and data model, from one process to three voters.

Embedded and standalone databases commit locally without running Raft. Replicated deployments use Raft across their configured voters.

  • In your process

    Embedded Rust

    Direct access to the engine with application-owned authentication and lifecycle.

    • Your Rust application
    • Kasumi engine, local commits

  • One server

    Standalone

    One-voter local installation with generated TLS identities, profiles, encrypted storage, audit, backups, and recovery tools.

    • TLS identities and client profiles
    • Audit, backups, and recovery tools
    • Engine, one voter, local commits
    • Encrypted storage

  • Three voters

    Replicated

    Three initial voters in independent failure domains, one Raft group per tenant, quorum-persisted writes, and a separate Control group for routing and operator metadata.

    • Separate Control group
    • One Raft group per tenant
    • Three voters, independent failure domains

Security and operations

Isolation by tenant. Every layer explicit.

  • Per-tenant encrypted storage

    Each tenant has its own policy, credentials, and encrypted storage. In replicated mode, each tenant also has its own Raft group.

  • Audit records

    Tenants keep separate audit records, and operators can inspect a tenant's audit stream.

  • TLS 1.3, mTLS, and pinned certificates

    Network access uses TLS 1.3 with mutual TLS and pinned server certificates. Installation generates the TLS identities and owner-only client profiles.

  • Credentials that expire

    Bearer credentials expire after one hour. kasumid credential watch keeps each profile renewed while the server is running.

  • Separate roles and endpoints

    The application profile reads and writes documents and cannot administer the database. Administration uses its own profiles on a separate endpoint.

  • Backups and recovery tools

    Installations include backups and recovery tools, with documented procedures for replica restart, member replacement, and restore from backup.

For agents

Give an agent a narrow data surface.

Kasumi's MCP endpoint exposes the same authorized core data operations as the SDK: five tools, and nothing else.

Calls use the installed bearer credential and current MCP protocol headers. The tool list is filtered by token scopes, and each call still checks the tenant's current policy.

Administrative operations stay on the separate native administrative endpoint. They are absent from MCP.

tools/list

  • kasumi_collectionsList collections
  • kasumi_getRead one document by collection and ID
  • kasumi_queryRun the same typed query language
  • kasumi_mutateCommit the same mutation batch as the SDK
  • kasumi_receiptLook up a receipt by idempotency key

Questions

About support plans

What does a support plan cover?

Help with running Kasumi in your own environment: installation and configuration questions, upgrade guidance, and investigation of problems you report, prioritized by the severity definitions above. The comparison table and the support terms list what each plan includes.

Is Kasumi a hosted service?

No. Kasumi is self-hosted software under the Apache-2.0 license, and you run it on infrastructure you control. A support plan covers help with your installations; it does not include hosting or operating them for you.

Do plans cover pre-release builds?

Yes. Kasumi's first production release is still in development and no revision is release-qualified yet, so plans cover current development builds today and continue through 1.0. The release ledger in the repository records what remains. Teams still evaluating can start with a design-partner pilot.

How do I change or cancel a subscription?

Self-serve subscriptions are managed in the customer portal, where you can update payment details, view invoices, and cancel. The support terms describe when a cancellation takes effect.

How are invoices and Japanese consumption tax handled?

Prices are shown excluding tax. Customers in Japan pay 10% consumption tax, calculated by Stripe at checkout, and every payment produces an invoice from Soramitsu Co., Ltd. that you can download from the customer portal. Enterprise contracts are invoiced under the signed order.

Is support available in Japanese?

Yes. You can write to us in Japanese or English, and we reply in the language you use.
