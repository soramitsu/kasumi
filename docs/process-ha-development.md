# Separate process HA development

This work does not qualify G09, G12, G13 or a production release. No installed
topology, authority, credential, certificate, release pin or domain outcome is
generated by these helpers.

## Installed inputs

`scripts/process_ha_topology.py` inspects a closed JSON plan with schema
`kasumi-process-ha-plan-v1`, a `binaries` object containing absolute `kasumid`
and `kasumi-authority` paths, and exactly nine `nodes`. Each node has exactly
`id`, `role`, `group`, and `config`. Roles are `data`, `control`, and `authority`,
with three processes per role and three distinct groups. Configuration paths
select original installed product configurations; this is not an alternate
product configuration decoder.

Inspection records original input hashes and the actual executable hashes.
It rejects shared or overlapping persistent/scratch roots, symlink roots,
storage outside the selected node's roots, shared database paths, substituted
physical verifier identities, mismatched original voter/peer rosters, and
duplicate leaf certificate identities even when PEM formatting differs. The
current leaf must match its configured peer pin. Keys and token files are not
read. Product configuration validation and actual TLS authentication are still
required; parsing certificate bytes for their leaf hash does not establish
certificate validity or trust. Reinspect with `verify_unchanged` before and
after each experiment.

## Process custody

`scripts/process_ha_owned.py` supplies `OwnedProcesses` as a bounded context
manager for a local experiment. Use an already admitted product executable and
its actual `serve <configuration>` command. Provision each installed node with
the product's explicit `provision-node` operation before normal startup. The
controller never opens or owns the database itself.

Each daemon gets its own process group, original command, birth witness,
executable hash, private log and durable receipt. Nested starts obey the
existing release runner's process ledger and admission seal. Interruption,
failure and normal context exit drain every owned group. Each restart has a
new original receipt; it cannot overwrite the prior crash. A crash targets
only a currently owned, live child after retaining the supplied observation
bytes. The controller records the observation hash and the actual SIGKILL;
the domain caller must independently authenticate and interpret the reply.

The controller reports `drained`, not a domain success verdict. It cannot
substitute for signed readiness, source fencing, target initialization,
single-winner recovery, fresh read-only inspection, native readback, or a full
24-hour workload. Its schema is intentionally separate from the release
acceptance schema, and `DOMAIN_ADAPTERS` remains unchanged.

## Product gap observed on 2026-09-27

The current `RuntimeConfig::validate` requires local tenants unless the node
is a recovery target. `RuntimeConfig::bootstrap` uses the same peer/voter set
for Control and data. `control_genesis::bootstrap` derives Control nodes and
tenant routes from that same local replication configuration. Merely allowing
an empty tenant list would not establish independent Control and data quorums.

The required product change is an explicit installed Control topology and
authenticated client boundary for data nodes, with Control-only processes
hosting no tenant or target storage. The dedicated process integration fixture
must provision nine separate roots and identities through current product APIs
and exercise actual service commands. Existing colocated runtime fixtures and
the Python process-custody tests do not establish that topology.

Run the development tests with:

```sh
cd scripts
python3 -m unittest -v test_process_ha
```

The topology cases use explicitly synthetic inputs. The custody cases execute
real Python child processes to test distinct ownership, ordinary termination,
SIGKILL/restart, interruption, and ledger sealing. They do not execute Kasumi
or establish any storage recovery outcome.
