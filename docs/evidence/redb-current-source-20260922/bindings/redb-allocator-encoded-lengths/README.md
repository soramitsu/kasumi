# Checked allocator encoding lengths

This is a target-only four-file candidate. It is not applied, compiled, or tested by this package. The original encoders and decoders are byte-for-byte unchanged; the manifest pins every serializer body independently and records the exact live-source bases. No compatibility format, migration, capacity policy, deadline, or workload is introduced.

`reserve_allocator_state` used to serialize the tracker and each buddy allocator just to measure them. It now borrows their existing metadata and calls checked length helpers. Btree bitmap and buddy formats store absolute u32 end offsets, so the helper checks every absolute end as well as pointer-sized arithmetic. The region tracker stores individual u32 child lengths, so its helper checks those fields independently and the aggregate against usize; it does not incorrectly impose a u32 total-length limit on that representation. Grouped bitmap length uses only its logical words, verifies that the words have backing, and ignores spare Vec capacity. Buddy length verifies the number of order bitmaps matches its emitted offset count.

The reservation method checks the allocator count against the current layout and computes all encoded lengths while holding the original state guard. Invalid geometry or arithmetic returns the existing `StorageError::Corrupted` before the method's first allocator-state tree insertion. It adds no `expect`, capacity error, or physical-admission bypass. This is a local pre-insertion guarantee: the surrounding transaction can already have performed other mutations before calling the method. Error-string allocation and the existing per-region scalar `Vec<usize>` are not claimed to be allocation-free.

Seven prepared tests cover logical bitmap boundaries and retained capacity after resize; missing bitmap backing; offset-header, offset-field and usize overflow; every supported buddy order with empty/partial/full regions and allocation/free/resize; missing order metadata; region-tracker count/bitmap boundaries including INITIAL_REGIONS and MAX_REGIONS with resize and roundtrip; and individual-length versus aggregate arithmetic. Tests use the existing test allocator observer around the actual helper calls and require zero allocations. Fixture setup and serialization occur outside those observations. None of these tests has been executed here.

The patch leaves the actual serializers intact. `RegionTracker::to_vec` still makes its own temporary child serializations, `BuddyAllocator::to_vec` retains all order images, and bitmap serialization retains level images while creating its result. `try_save_allocator_state` still creates the full prepared allocator copy. The existing scalar length inventory, zero-filled reserved values, tree insertion/removal/checksum scratch, old/new allocations, allocator/cache resident metadata and page payloads still require their own admission and peak bounds. This optimization removes the reservation pass's serialization-to-measure; it is not a total memory or RSS estimate.

The maintenance design in the source-pinned documents listed in the manifest remains open. Protecting extension bytes through `DiskWork::Maintenance` alone cannot protect already-grown allocator free pages from foreground allocations. A coherent restricted maintenance owner must reserve both real free-page capacity and extension allowance on the exact physical file, retain that capability through rollback/close/uncertainty, and fund the complete source-derived COW and allocator-state workspace before effects. No maintenance budget, numerical total, implicit foreground restriction, or reserve implementation is inferred by this candidate.

Static validation consists only of target-file rustfmt, exact unchanged serializer/decoder bodies, exact live/base matches and `git apply --check` against master. The parent must review and apply this patch, then run the original vendor gates with the prepared tests. Static success is not test or release qualification.
