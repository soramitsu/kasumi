# Remove obsolete management recovery

Read-only source review began at fe4ee8771cbcb6374264f0df70489149733bccb3 in /tmp/kasumi-production-strict-reconcile. Root advanced to 1ff2fe2691bb3adfe74da762b3a64204c941ebfd while reviewing; all reviewed production implementations were identical across those revisions (api.rs changed receipt tests only). No runtime source was modified and no Cargo/native test ran.

## Confirmed dependencies and defects

1. administration.rs:133–168 exposes PrepareRestore, InitializeRestore, CompleteRestore, RetireSource and ActivateRestore through ManagementCommand. execute_retirement_lifecycle:643 requires the same RequestContext against source retirement and target authorization. PrepareRestore:940 similarly uses source authorization and providers to prepare another incarnation. These conflict with exact credential-resource binding. NativeAdmin::manage in rpc.rs:1006 adds a multi-generation ManagementResponseFence, which repeats the same problem.
2. The old family exclusively owns GenerationDescriptor, runtime.generation/descriptor, generation_path/create_generation_file, verify_restore_peers, load_generation, and ProviderFactory. load_generation:1837 attempts Serving then falls back to RestorePreparation after any error and opens legacy local/replicated APIs. It is also called from Administration::reconcile:2118, so deleting just dispatch leaves a live fallback decoder/opener behind.
3. Canonical TargetRecoveryRuntime uses its independent journal, exact materialization file identity, retained activation projection and fresh Serving lease. target_serving_runtime.rs:302 registers the resulting database only in DatabaseRegistry. Administration::current:474, local_observation and reconcile use separate generations/active/enabled maps. Thus native data can reach a canonical target while administration/metrics resolve the old source or try the obsolete descriptor path. Copying target handles into the Administration owner map would create competing drain/reopen ownership and is not a clean replacement.
4. TargetServingReplica::check in bootstrap_target_serving.rs:32–62 treats suspension and original voter membership as permanent identity. confirm_local_application in kasumi-raft/src/local_applied.rs returns latest applied membership, not historical membership at activation. Suspension, adding a learner or replacing a voter therefore triggers target owner closure and repeated failed reopening. This is a separate required prerequisite, now assigned for implementation in /tmp/kasumi-target-operational-membership.
5. Administration::new/publish_target installs archive destination aliases on its databases. Canonical target serving registration does not install these aliases. Later retained-history reads/retirement verification need the installed target destination set as part of setup before exposure.

## Canonical interfaces that must remain

- rpc_recovery.rs NativeRecoveryControl and recovery_runtime.rs ControlRecoveryCoordinator implement typed start/status/resume/stop/read_phase with the exact Control credential, durable dispatch inputs, issuer commands, target attestations and phase response fences. recovery_cli.rs and kasumi-client/src/recovery.rs already expose this family. Use it directly; do not translate legacy ManagementCommand JSON.
- RecoveryRoute installs distinct target, issuer-administration, source-application and source-custody credential sources. Planned retirement dispatch separately obtains and verifies source custody evidence (recovery_runtime.rs:499 onward). SourceUnavailable selects the separate issuer fencing workflow. Keep those independent checks and original phase deadlines.
- rpc_retirement.rs retire_source_rpc, retirement_status_rpc, verify_retirement_receipt_rpc, abort_retirement_rpc and closed custody operations address only the explicitly selected source incarnation. They do not require a live target database on that server and must remain, along with InstalledRetirementSource transitions and native client methods.
- rpc.rs read_restore_lineage and the native data client's lineage read remain independently bound to the currently selected database resource.
- local_recovery.rs / local_recovery_tests.rs and stopped-installation standalone CLI remain the standalone coordinator; no distributed fencing claim is added.

## Implementable removal sequence

1. Fix activated target operational-state validation separately, retaining exact activation/origin/physical bootstrap proof, current issuer admission, permanent-stop checks and worker/storage drain. Keep a changed current membership separate from authenticated original bootstrap. Add real suspend/resume, learner and replacement/restart regressions before claiming maintenance works.
2. Split ordinary administrative access from ownership. A short-lived administrative selection should borrow the exact database plus its existing application store from DatabaseRegistry after authorization, or the existing separate Control database for the reserved Control resource. The Raft storage_domains application accessor already supplies the store; no provider reconstruction is needed for backup/key rotation/membership. Pin this same selected handle through execution and response release. Retain authorization revocation and old-instance gates; never re-resolve a new database after dispatch. Original startup/provisioning owners and TargetRecoveryRuntime keep exclusive reopen/drain responsibility.
3. Make current/authorized_database, ordinary execute and response_fence select this shared current handle. Remove Status.incarnation: current status is credential-bound; prepared/closed recovery inspection uses typed recovery/target/custody status. In Administration reconciliation, process only installed original/provisioning owners. For a route to a canonical target, observe the exact already registered target and mark availability from that handle; do not open paths, create providers, infer ownership from Arc counts or publish over another runner's handle. A routed but unavailable target remains unavailable. Control-topology projection and issuer activation retain their existing authority roles.
4. Update administration_observability.rs to read bounded exact registry handles matching each committed route incarnation, alongside the private Control handle. Keep response-owned store/gate fences. Install approved destination aliases in canonical target setup before registration. Ensure target close detaches only its own exact registry entry and cannot shut down an unrelated original/target owner.
5. Delete the five obsolete enum variants and all dispatch branches, lifecycle_source, execute_retirement_lifecycle, source/target retirement fields of ManagementResponseFence, GenerationDescriptor, verify_restore_peers, load_generation, generation_path/create_generation_file, runtime.generation decoder, administrative_generation node-ID helper and its obsolete tests. Preserve generic native retirement and its stack-bound tests. Drop ManagedTenant descriptor/provider/custody_provider fields and ProviderFactory once no readers remain; bootstrap and lease are still required by original enrollment/ownership. Remove the descriptor discriminator from original_serving_runtime because its map now contains original owners only.
6. Preserve the readiness checks used by PrepareTenant/InitializeTenant/ActivateTenant. The old RestoreReadinessProvider is also used at administration.rs:1624, so remove only its descriptor branch first; rename the remaining internal protocol to enrollment/provisioning readiness directly (cluster.rs types, install method, RESTORE_PATH and runtime registration), with no route alias. No change is needed to canonical target signed readiness/phase protocols. Coordinate runtime.rs edits with the cold-start owner.
7. Remove RuntimeConfig.max_prepared_generations_per_tenant/default_prepared_limit and example field: it has no remaining implementation reader even now. Coordinate this and ManagedTenant/ProviderFactory constructor changes in runtime.rs with the cold-start owner. Remove obsolete descriptor documentation from docs/node-file-envelope.md. Rewrite docs/administration.md recovery section around control-recovery and planned-retirement, remove the one-credential steps and prepared-generation Status example. Fix its stale environment-token/OAuth-only/init descriptions from the canonical current profile/init contracts. Keep no compatibility aliases, migrations or legacy decoders.

## Required regression evidence

- Deserialize each of the five former operation names and Status.incarnation: all fail explicitly, before any files, providers or leases are acquired.
- Exercise actual canonical encrypted target activation/local confirmation/route publication; target-native credential can perform ordinary management status/backup/key operations and metrics observe its real group. Source, custody and Control credentials cannot substitute for the target.
- Race target expiry/stop/detach with an admitted management request and serialized response: retained old instance stays closed, response is fenced, no alternate generation is selected; target runtime alone drains/reopens.
- Use independent source and target hosts for planned retirement; retain source-only native status/abort/proof and lineage tests. SourceUnavailable still works with the source absent.
- Restart after canonical activation and after operational suspension/learner/voter changes. Resolve only journal-owned physical target identity; old generation descriptor/path presence cannot enable a route. No fallback path and no store creation on missing canonical files.
- New-tenant approval/readiness/initialize/activation still works after removal of restore-named readiness and constructors.

This is an implementation map, not evidence that those gates passed.
