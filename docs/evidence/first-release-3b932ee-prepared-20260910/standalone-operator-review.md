# Standalone operator ownership source review

Reviewed implementation: 7234f9a49cfd91e91f78d40efe96ea259ebc9527, integrated with the canonical singleton initializer at root be04883f9c0c6ba999e0201c3a5fef4e331475bb. This is a bounded source review, not a test or production acceptance result.

No new blocking ownership defect was found in the reviewed operator acquisition, normal error, caller-cancellation and drain-cancellation paths. Public initialization, administrator recovery, key/signer/certificate rotation, key backup and local recovery dispatch into the retained LocalOperator registry. Losing the reply cannot abort its registered task. Successful replies carry only an already-drained result. Ordinary preparation errors are acknowledged or retained by that same registry.

OperatorState records the exclusive installation lock and physical node before the first catalog await. Each returned singleton, audit writer, pair and database enters retained Resources before subsequent fallible work. Control is opened strictly and cached for the operation. Local target acquisition retains its node and pair, and drains pending resources on every captured error; successful targets own their own Resources until their explicit shutdown. Restored operational nodes are retained by the surrounding operator before opening another tenant. Both operator fields and Resources put the installation lock after resource-bearing owners in drop order.

Initialization publishes its immutable preparation marker before node creation. Its completion configuration and installation marker publish only after pending resources drain; the installation lock remains held during publication. Failure leaves the exclusive incomplete installation rather than treating it as a new or recoverable installation automatically.

The tests exercise real owner-only installation files, file keyrings, encrypted storage, actual audit writers and exclusive NodeStore reopen. The singleton failure uses a distinct valid wrapping keyring to reach an actual encrypted catalog decrypt failure. The Control-pair failure is injected only after both actual stores are acquired and retained, then verifies immediate physical and Control reopen. The initialization error occurs after an actual audit writer starts and rejects publication of completion artifacts. Cancellation tests discard the public reply and one registry drain while paused after physical acquisition, prove installation and node-file exclusion, then release the task, drain it and reopen the same installation.

Those pause points precede the substantive rotations or recovery phase mutation. These tests do not establish mid-file-rotation atomicity, process-kill recovery, cancellation at every local recovery phase, leaf worker panic propagation, or failure-domain durability. Registry-level buffered outcome tests cover distinct handoff properties. The global drain is a quiescent-admission operation; its cancellation tests serialize against the existing local recovery drain regression. Test checkpoints have release-on-drop guards, preventing a failed assertion from intentionally stranding another test's registered operation.

Remaining known limits are accurately recorded in docs/standalone-operator-ownership.md and docs/startup-drain-outcomes.md: several leaf shutdown interfaces erase worker outcomes, and direct cancellation of an unregistered internal finish future is not the public-operation contract. This review found no basis to claim those limits fixed by the operator patch. No Cargo, Rust tests, native server, TLS process, container, VM or heavy command was run for this review.
