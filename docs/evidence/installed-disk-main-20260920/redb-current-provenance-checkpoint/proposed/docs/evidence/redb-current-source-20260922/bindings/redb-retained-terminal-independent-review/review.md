## Result

No additional confirmed correctness blocker found in this narrowly documented vendor prerequisite. This is not approval of production staging adoption or a claim that any prepared test passes.

The first operation is recorded and transaction.completed is set before terminal effects, so WriteTransaction Drop cannot silently replay abort. Both commit and abort execute by mutable borrow with the real transaction still in the owner. A live normal table borrow prevents acquiring the mutable terminal receiver. The table-work accessor returns None after the first terminal operation. Repeated commit/abort calls only borrow the first operation/outcomes.

Commit uses the existing durable commit helper. CapacityDenied and TransactionPoisoned are the only typed refusal paths that trigger a single rollback; the original refusal remains in the terminal cell and rollback keeps its independent original result/panic. Successful rollback can settle that refused operation without rewriting the primary outcome as success. Other errors or panics do not attempt rollback. The allocator latch is armed before the attempted operation and is disarmed only after a returned successful commit/abort/rollback; its existing poison-tolerant invalidation remains active for uncertainty. No new publication protocol, durability relaxation, compatibility decoding or error reclassification was found.

The winning-header panic test injects after the second header write has actually synced, recovers the committed row from an independent crash-image copy, and keeps the uncertain original transaction/database. This is a useful counterexample to assuming a panicked commit was aborted. The other fault tests preserve original I/O, refusal and rollback payload identities, and compare backend counts before/after retries. All five unresolved fixtures use fixed retained test custody and positively require Database::close to return Busy with no backend close.

## Lifetime and production obligations

1. The wrapper is not self-retaining. Its documentation correctly requires a pre-admitted external fixed owner/census before dispatch. Dropping a Retained wrapper still destroys WriteTransaction and its guard; that is not a supported cleanup path. The production operation owner must remain reachable across caller cancellation and panic, and must not leave the wrapper solely in a fallible local variable.
2. Settled is only the actual transaction terminal result. It does not release the live writer guard, database, backend, error backing, allocator/cache memory, or memory charge. In the present type, the transaction remains installed until the wrapper is disposed. The next staging slice needs an explicit actual-disposal/retained-close boundary before claiming drain or reusing admitted backing. The existing consuming Database::close can itself unwind while consuming ownership; this prerequisite does not solve that.
3. WriteTransaction and its namespaces retain TransactionGuard Arcs. Keeping the wrapper therefore keeps the actual writer registration and makes explicit database close Busy. Existing field destruction eventually releases the guard and allows a new writer before every trailing bookkeeping field/backing is necessarily gone; consequently that writer-slot event must never be used as proof of total memory retirement. A future outer owner must retain its full envelope through actual complete disposal and final allocation destruction, as with the independently reviewed final-Arc/Box funding tails.
4. Transaction construction, caches, page trackers, savepoint bookkeeping, record buffers, original I/O payloads and opaque panic payloads still need a concrete mandatory admitted memory bound. retain itself only introduces inline observation state; it cannot retroactively admit allocations already made by begin_write or mutation.
5. All twelve currently listed Kasumi production consuming commit call sites and the central NodeDatabase begin boundary must directly adopt the supported owner together. Upstream consuming APIs remaining available are not permission for a Kasumi fallback. The existing unchanged 512×256/60-second/80 MiB and 40×768 KiB/384 MiB workloads remain release gates after the actual bounded staging implementation exists.
6. Eight prepared tests, the existing redb transaction/admission/failure suites, supported default/all-feature builds, strict lint, and provenance update remain required on the exact applied source. The static patch receipt is not runtime evidence.
