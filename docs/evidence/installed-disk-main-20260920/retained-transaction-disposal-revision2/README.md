# Retained transaction disposal, revision 2

Target-only prerequisite. No actual Rust source edits, Cargo builds, or tests were run by this author. The original revision remains preserved and is rejected by the sibling authority-review receipt. This revision is a complete patch against the current master sources, not a patch to apply after revision 1.

`RetainedWriteTransaction::dispose_settled` requires a borrowed matching `RetainedDatabase`. A crate-private helper checks exact Arc allocation identity for both the transaction tracker and TransactionalMemory, and permits only Open or WaitingForTransactions ownership. The witness remains borrowed for the entire synchronous disposal operation. It exposes no new database access and prevents Database::drop from handing physical backend close to the transaction's destructor. No reference-count heuristic or check-then-drop window is used.

Preterminal, uncertain, or wrong-database requests do not take the transaction and do not enter disposal. Matching positive commit/abort/rollback settlement permits one actual transaction destruction. The first phase result or original destructor panic is retained, and later calls only observe that phase. The terminal and rollback cells stay in the same wrapper, preserving their original error identities. TransactionGuard is the last WriteTransaction field, so table/savepoint/deferred-page field backing retires before writer availability is released. Writer availability alone is not credit release: the actual wrapper and its retained outcomes remain admitted until their allocations are independently retired.

Physical backend close is deliberately left to the exact retained database's explicit close phases. This fixes the rejected revision's destructive deferred-close path, which discarded returned backend errors and could lose physical owner custody while catching a destructor panic. A caught internal transaction-destructor panic remains incomplete disposal; it does not prove physical cleanup, reconstruct the consumed transaction, or authorize replay. The matching database remains separately owned during that call. The API is not a self-retaining lifetime mechanism; the production aggregate must keep both owners and all original outcomes in admitted custody through cancellation/unwind and final retirement.

Tests use real redb files and the same original terminal workloads:

- The existing positive commit/abort and capacity-refusal cases retain their original reports through explicit disposal and actual writer reuse. The callback-panic/poisoned-transaction fixture now does the same while retaining its original callback payload.
- Every one of the five original uncertain cases refuses disposal with a matching database in both Open and WaitingForTransactions state, preserving the same transaction pointer and unchanged actual I/O/settlement counts. Their fixed test custody retains the actual transaction, retained database, original file, and outcomes.
- The new preterminal case leaves the actual transaction usable, then permits disposal only after positive abort.
- A new wrong-database case verifies no transaction take and no I/O/backend calls for either database, then proves matching disposal and writer reuse. The backend's existing panic marker is armed during disposal, so accidental backend-close entry would be observable; its mode is reset only after unchanged counts prove no close entered.
- A new matching WaitingForTransactions case verifies that physical close phases stay NotEntered while the writer is live, that the witness can dispose the settled writer without reopening database access, and that only subsequent explicit database close releases the backend once.

The rejected deferred-backend-Drop panic test is removed; it was not evidence of retained physical custody. Existing retained-database tests remain responsible for exact returned close-error and panic custody. There are eleven retained-transaction tests in this proposal (eight existing, three new), with no reduced workload or extended deadline.

This does not migrate Kasumi's twelve production commit call sites, change consuming upstream dependency behavior, supply an admitted production transaction/queued-writer census, derive a general transaction-memory bound, or qualify staging batches. The eventual first-release adapter must directly use retained database/transaction/spool ownership together; there is no compatibility fallback in this new disposal API.
