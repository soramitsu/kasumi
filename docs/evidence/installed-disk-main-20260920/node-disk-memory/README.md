## Canonical ownership and API

`NodeDiskMemoryAdmission::reserve_installed(self: Arc<Self>, bytes)` is mandatory. The returned opaque resident lease must retain the real resource governor. The implementor reserves its own lease box overhead before allocating that box; it consumes no operation slot. There is no default/no-op governor, optional token, policy-equivalence identity, or independently created production adapter.

NodeDisk and ScratchDisk open borrowed configuration with an explicit `Arc<dyn NodeDiskMemoryAdmission>`. Their registries compare exact Arc resource identity on reuse before acquiring another charge or cloning configuration/paths. NodeStore creation, owned-empty initialization, and existing-file open also require persistent and scratch owners to carry the same exact memory Arc before touching the file. The companion engine adapter implements the trait on the actual `Arc<MemoryCore>`.

`DiskOpenError::RegistryBusy` is an inline, nonallocating preparation result, distinct from `Failed(anyhow::Error)`. The production and cfg-only isolated `open_fixture` methods are single-attempt. Device registry contention propagates as the same typed variant. The explicit cfg-only `test_utils::retry_disk_registry` setup helper retries only that variant, for at most five seconds with a one-millisecond sleep. It never retries provider or file-lock errors merely because their io kind is WouldBlock. Generic fixture convenience setup uses this helper while preserving the same configuration, directory custody, and core across attempts.

The canonical fixture signatures require memory explicitly: NodeStore create/open receive `(path, id, memory, scratch)`, owned-empty initialization additionally receives its existing identity, cleanup receives `(path, id, memory)`, archive receives `(root, memory)`, and backup destination receives `(root, limit, memory)`. NodeDisk/ScratchDisk expose `memory()` for deliberate owner propagation. Trusted generic fixtures select N=16,384 census entries, H=256 file owners, D=64 depth, name=255. Installed production policy remains N=1,000,000 and H=4096. Store fixtures use a separate explicit bounded metadata-only TestDiskMemory (normally 256 MiB/4096 leases); they do not increase application byte/disk payload budgets.

## Admission ordering and real lifetime

New NodeDisk owner and registry leases are acquired before opening roots, cloning retained configuration/pathnames, walking ancestors, or constructing the first census. A single nonblocking registry guard serializes preparation and publication. A cached owner requires identical policy and memory identity, and its prepared root bindings are checked before reuse. Reconciliation can hold the old and replacement ledgers simultaneously; both are funded by the same retained envelope. Handle acquisition already reserves map capacity before physical creation; publication now holds the state guard before preparing its additional paths/Arc.

The global NodeDisk registry is a charged linked list, with one independently charged entry per actual retained owner. NodeDisk intentionally remains installed after facade/runtime handles close: its descriptor locks, census, and resident leases remain together. This patch does not pretend runtime shutdown deallocates that retained installed state.

DeviceDisk uses charged linked entries instead of retained global HashMap capacity. The shared Device allocation and registry entry have one resident charge; each actual owner registration has another. Registration removal deallocates its list node before dropping the returned lease-bearing value. Dropping an uncertain/pending registration preserves the existing sticky device failure/promise semantics. Reusing a device requires the same exact memory identity and charges only the new registration, not another device. List removal/destruction is iterative, avoiding an unbounded recursive chain drop.

ScratchDisk also retains its installed owner strongly, matching NodeDisk. Its charged registry entry keeps the actual owner allocation, prepared path, directory descriptor, device registration, and memory lease together until process exit. Exact configured path/policy/core reuse returns that same Arc without another admission. Public Arc drops and arbitrarily retained external Weak observers therefore cannot separate its allocation from its funding. Per-file scratch byte/file/promise charges still release after actual file ownership ends; metadata stays installed.

Revision 1's removable Weak registry released its allocation envelope too early if an external Weak remained after the last public strong owner dropped. The complete original patch/manifest/source is immutable under `revisions/v1`; revision 2 removes that lifetime claim and the Weak pruning/destructor algorithm. The cfg-only canonical `ScratchDisk::fixture(directory, memory)` and `isolated_fixture(directory, max_bytes, memory)` require an explicit path whose private TempDir remains owned by the caller. ScratchDisk stores no TempDir, and production Drop never removes configured directories. Fixtures returning a long-lived test object retain the directory in that object. A regression proves the caller removes its fixture name even while installed metadata remains funded. Store fixture tests now create one explicit scratch owner per intended scope and pass it through backend crash/reopen helpers instead of creating new temporary directories at each reopening. No payload or metadata caps were raised. Unique installed directories still consume separate aggregate resident leases.

## Planning components and coefficients

`DiskMemoryRequirements` returns four independently owned components: `owner_bytes`, `registry_bytes`, `device_bytes`, and `registration_bytes`. The memory provider adds its own boxed-reservation overhead to each acquired component. A fresh isolated NodeDisk plus ScratchDisk therefore needs eight real leases. Reused physical devices omit only an already existing device charge. Cached NodeDisk/ScratchDisk owners acquire nothing. Fixture planners must count actual unique owners/devices, not add unused cached-owner headroom.

All calculations use checked arithmetic and actual configured path byte lengths. Let S(T) be Rust `size_of::<T>()`, N census cap, H file-owner cap, D depth, and M=name bytes+1. The node envelope contains:

- Two ledgers, each `4*max(N,4)*(S((Identity,AccountedFile))+16)+4096`, covering retained and replacement capacity and table resize peaks.
- One live-owner table with the same table formula for H `(Identity,Weak<FileOwner>)` entries.
- H+1 owner workspaces. Each includes the actual FileOwner/Arc size, 4096 native handle/mutex workspace, rooted-name/relative/parent-name bytes, and bounded CString vector/box preparation. The additional owner funds publication preparation.
- D census cursor/directory-stream workspaces: 64 KiB per native directory stream plus four actual Cursor sizes, a copied bounded name and an allocation allowance.
- Configured root path/label copies, actual root/config structures, bounded ancestor descriptor vectors, and a fixed 64 KiB acquisition workspace plus actual NodeDisk Arc storage.

The namespace binding contributes 32 bytes to AccountedFile, FileOwner, and Cursor. The standalone copied-shape helper now measures AccountedFile=72, ledger pair=88, FileOwner=200, Cursor=48. For a representative root, N=1M/H4096/D64/name255 gives 1,016,139,012 bytes (969.066 MiB) of the formula workspace before the actual NodeDisk Arc base and independent registry/provider fees. An explicit 2 GiB new-install total leaves 930,018,044 bytes after that estimate plus 192 MiB audit pools, before core/startup/scratch charges. This is an estimate, not a substitute for the actual compiled helper or detected host pressure limit. The prior estimate and provenance are preserved under `before-namespace-rebase`.

Native directory-stream/mutex and std HashMap growth coefficients require qualification on the supported toolchain/platform; comments do not claim a stable Rust allocator-layout contract. The implementation continues to allocate bounded collections as needed; funding their maximum workspace does not eagerly allocate a million-entry map.
