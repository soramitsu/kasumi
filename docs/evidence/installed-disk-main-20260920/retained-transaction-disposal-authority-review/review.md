# Retained transaction disposal review

Verdict: one P1 blocker. Do not apply patch 6bf815e71c839cb1105a27573b330dc5a6ff0a3a02462f49e0350701886a8bb4 as proposed.

At proposed retained_transaction.rs160–167, positive commit/rollback settlement allows destructive `drop(self.transaction.take())` without retaining a live Database owner. The proposed actual_deferred_close_panic test explicitly drops the Database first. Then TransactionGuard::drop (db.rs356) takes the final deferred TransactionalMemory from TransactionTracker::end_write_transaction (transaction_tracker.rs130), calls close_database (db.rs1241), and drops that local memory/backend after return or unwind. close_database uses `let _ = mem.abandon()`: a returned original backend close I/O error is discarded and disposal records Returned(Ok(())); a panic is recorded only after the underlying physical owner has been destroyed by unwinding. The new test injects panic after FileBackend::close succeeded, so it does not demonstrate preservation when close is physically uncertain. Keeping only a panic report and temporary pathname does not retain the actual backend.

Required correction: make disposal require a borrowed, matching live RetainedDatabase witness, including its WaitingForTransactions state, and compare exact transaction-tracker plus TransactionalMemory identity before taking anything. The witness must remain borrowed throughout disposal so no deferred Database destructor path can run. Do not substitute a reference-count or separate liveness check. Physical backend close must remain the explicit separately observed RetainedDatabase::close phase. If an API instead supports disposal after Database drop, it must independently retain and observe the actual deferred backend; a catch around destructive Drop is not enough.

The rest of the narrow implementation is coherent: terminal/rollback outcomes stay in the original wrapper; unstarted and uncertain settlement skips disposal; the first disposal phase is recorded before Drop, a caught destructor panic cannot later become successful; and moving the transaction guard last delays writer release until table/savepoint/deferred-page field retirement. Writer availability is not memory-credit release: an external admitted census must keep its charge until all actual owner/report allocations retire. This does not establish the general transaction memory bound or migrate production callers.

Static evidence: all three manifest base/proposed hashes match, actual source still matches all three bases, patch SHA matches, and git apply --check passes. No actual source edit, Rust build, test, or Cargo invocation occurred. The new and strengthened tests were reviewed but remain unexecuted by this reviewer.
