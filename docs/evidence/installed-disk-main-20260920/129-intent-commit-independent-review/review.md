# Independent review of original intent-commit diagnostic

Verdict: approved for diagnostic integration with the exact limitations below. No implementation blocker found. This is not a cause attribution or a correction of the original write deadline. The immutable original README says no mutation; root agreed to correct that wording in the combined successor README while preserving this frozen evidence.

The proposal retains the original prepare_next result, operation/phase/command IDs, current-leader selection, one original lifecycle_control call, dispatch-limited context and every success-path intent/resolution assertion. Prefix and suffix comparison confirms those bytes are unchanged. Exactly one write remains, with no added await. LifecyclePhase and UUID are copied before moving the original command. The four-field route snapshot guard is dropped before awaiting the write. The pre-call Instant and scalar capture cannot refresh the verified authorization or production timeout. Call::wait still uses the existing ten-second response wait from service.rs; the entire request and failure report are not thereby guaranteed to take exactly ten seconds.

The failure branch only reads local state through the existing APIs and then panics with the original error. It does not request quorum, call recovery resolution, construct credentials, retry a request, admit new work, pause, reconcile, close, drain a child, or release storage/memory credit. The local BTreeMap lookup uses the original command UUID and copies only the matching intent's identity/phase/revision/accepted time/original lifetime; no retained row is treated as verified authority. Generation is access-fenced. All original database and physical fixture owners remain held by Fixture throughout reporting. Metrics and local state are independent observations, not an atomic snapshot or proof of why Call::wait expired.

Snapshot limitations are substantive: NodeDisk::snapshot takes its state and device locks and synchronously queries filesystem availability. On an already-poisoned state mutex, NodeDisk::lock_state records Failed and marks its device owner uncertain. ScratchDisk::snapshot's poisoned-state path also fails the owner. DeviceDisk::lock records an already-poisoned device mutex. These are existing fail-closed latches, not pure side-effect-free reads. They cannot clear failure, reconcile charges or cause a child drain. Normal unpoisoned paths gather fields without creating/releasing reservations. AdmissionSnapshot locks and reads the fixed charge slots and sampling clock, without taking the refreshing check_release path. The vote diagnostic formats the existing32-slot history under its mutex; it does not advance or retry a vote.

Reporting uses ordinary synchronous locks, filesystem-space queries and formatting/output allocations. It may block or panic independently after the original failed call; the original runtime request budget is unchanged, but it supplies no upper bound for diagnostic reporting. It does not reveal the pending child's exact I/O/await location or prove a matching local intent has quorum durability. Success-path overhead is confined to scalar/metric capture and Instant. Root explicitly accepted these existing snapshot semantics and will state them in the combined package rather than claiming mutation-free or deadline-bounded reporting.
