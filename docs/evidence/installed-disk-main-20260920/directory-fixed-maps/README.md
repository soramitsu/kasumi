The former `4 * count * (size + 16)` map estimates are replaced by two preallocated std HashMap banks for inode enrollment and two preallocated banks for live Weak registrations. Each inode bank is funded at the full retained `2N + R` capacity. The inactive bank receives the existing logically smaller `N + R` census, so no third map is allocated and the new active bank never needs expansion after publication. The existing million-file, 4096-file-handle, 4096-directory-handle, depth/name, disk and memory policy values are unchanged in this slice.

The wrapper exposes no mutable HashMap, entry or extend path. Every absent insertion requires both a logical slot and `capacity() > len()` before the filesystem effect. In the pinned Rust 1.97.1 / hashbrown 0.17.1 implementation, capacity is items plus growth_left; that is a no-resize certificate. Existing-key replacement uses get_mut and mem::replace because native HashMap::insert can reserve before checking occupancy. When tombstones exhaust growth but logical space remains, the wrapper copies into its already-funded spare, validates space, swaps, then drains the former bank. A reset guard also drains partial copies on returned error or unwind before preparation can release State. Thus duplicate Weak registrations cannot survive preparation and postpone actual last-Weak retirement. `clear()` alone is insufficient for an empty tombstone-depleted table; reset uses drain Drop to restore all control bytes/growth.

Initial census and reconciliation write only into the inactive bank. Reconciliation owns State throughout preparation, traversal, final cancellation and shared-promise checks; the active ledger and old counters remain intact on failure. The shared promise transition succeeds before the bank swap and old-entry retirement. The replacement candidate consumes no additional table backing. Tests cover cancellation after a real partial candidate, failed physical census, logical candidate limits, full retained capacity after swap, and preservation of the old ledger.

Pinned requested-allocation geometry is derived from exact `(Identity,V)` size/alignment, the 7/8 load rule, power-of-two buckets, control bytes and maximum supported control-group width 16. The 16-byte Identity key excludes tiny-element exceptions. Native aarch64 uses group width 8, so the formula includes a small conservative difference rather than reducing a heuristic coefficient. Initial try_reserve checks capacity>=limit, and no other resize is authorized. The existing 4096-byte per-allocation platform allowance remains explicit and unqualified; table requested bytes do not prove the allocator's physical footprint or process RSS. New inline Map/Banks state is included through actual NodeDisk size.
