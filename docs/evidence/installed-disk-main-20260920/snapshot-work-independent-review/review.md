# Independent snapshot work foundation review

Read-only review of foundation.patch SHA256 047dcc8abcff53eff8eee12d663ac9be41a66cedaa1902c7a6fb35e116a90f80. No source changes, builds, or tests. Reviewed all four proposed files and seven test bodies. Target-only foundation remains unqualified for production.

## Confirmed findings

1. **Funding can release before actual owner backing destruction.** In proposed admission/snapshot_work.rs:164–175, Owner keeps its Reservation as its final field inside Arc<Owner>. At final strong drop the reservation publishes byte/operation/ledger credits before the outer Arc allocation is deallocated. Concurrent admission can therefore reuse that envelope while its previous allocation is still alive. This is the same final-owner retirement issue corrected separately for FileOwner. Use an explicit final-owner/destruction protocol that frees the actual covered allocation before releasing its charge. Merely making the lease the last field is insufficient. Add a deterministic final-destruction gate proving credit is unavailable until real backing retirement, including concurrent report/delivery drops.

   The charged cancellation allocation has a related existing drop-order path: prepare_snapshot_work attaches a QueryCancellation clone to the core Charge at lines594–605. Current admission.rs Reservation::drop releases credits and the state lock before dropping that Charge (lines1015–1035). At normal final Owner destruction this can be the final cancellation clone, so fixing only the Owner Arc tail still leaves cancellation allocation alive after credit publication. Retire that covered backing before publishing the released capacity, preserving pressure cancellation and lock order.

2. **Complete typed failures remain in the strong census after ready().** Proposed snapshot_work.rs:439–442 joins and completes trusted cleanup, but does not call retire_complete. A typed failure with no output makes completion() return Complete. claim() returns its report early on resource.failure, and dropping the delivery/report only cancels/drops their external Arcs. Thus the core→census owner→core/Reservation cycle survives, occupying a fixed census and operation slot until the caller performs an extra explicit drain. Minimal correction: after ready finishes, retire_complete when its completion is Complete; successful unclaimed outputs remain Retained. Add capacity-one coverage: start a failing job, await ready/observe original failure, drop all views, verify census and operation reservation are released and the next job is admitted, without requiring a redundant drain of an already Complete result.

## Checks without an additional finding

The actual child handle is retained before suspension; join polling is in place; resource locks are avoided while a child is still running; failed preparation returns a generation-checked slot; stale reports cannot retire a replacement generation. finish serializes access to its single proxy waiter. Its ClearWaiter is declared after the serial guard and therefore clears the caller waker before the serial mutex unlocks on cancellation/completion. Opaque-panic census retention is intentional and explicitly documented, not an accidental uncharged leak. The trusted adapter, Tokio workspace, arbitrary-payload, and absent production/shutdown-adapter limits are honestly documented; this review does not claim to qualify them.

A proxy Waker may retain its WorkWake Arc through external wake activity, so the final lifetime correction should explicitly cover actual proxy-waker destruction as well. This is a boundary to verify with the correction, not a separate blocker based merely on an untrusted external SnapshotOperation implementation.
