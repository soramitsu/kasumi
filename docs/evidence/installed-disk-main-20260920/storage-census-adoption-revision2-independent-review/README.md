## Why the original blocker is closed

The release latch now belongs to OpeningState/WriterState and uses the same mutex as the actual terminal observations. The concrete state machine provides the required attempt binding without a new numeric generation: once a terminal report is releasable, no later effect can inherit that permission. The independent census generation still protects slot identity and reuse.

For opening (`storage_opening.rs:116–130,261–267`), retirement first seals admission and only writes release permission if try_lock obtains the real owner state. Drive clears that permission before every close attempt unless the retained redb state is already Closed. A shutdown error generated by the initial retirement's close therefore remains unacknowledged even when backend release establishes Closed. A later facade can observe and release that unchanged Closed report. A busy opening worker cannot be acknowledged, cannot block this state access, and cannot later reopen through another facade because stopped is already set. Repeated uncertain close remains conservative and does not replay vendor phases.

For NodeTables (`storage_opening.rs:428–447,459–469`), the worker holds the actual WriterState guard through serial wait and execution. Retirement cannot write permission while it is active. If the request is still Queued, retirement changes it to Cancelled under that same guard before acknowledging the no-work state; a second facade then cannot enter begin/body/terminal. If a worker wins the race, run clears permission before entering outer execution, and the competing retirement fails try_lock. It cannot acknowledge the later body or terminal outcome.

For deferred abort/disposal (`storage_opening.rs:316–338`), every not-yet-positive disposal clears prior release before looking up the matching database witness or entering abort/disposal. The later drive decision observes this same guarded flag. Busy witness access returns retained with permission cleared. An uncertain terminal, interrupted disposal or missing witness remains undisposable even after explicit release. The no-transaction branch still refuses uncertain outer panic or entered begin. The early true branch is limited to the original positive disposal_complete observation, which can produce no new terminal effect.

## Disposal after database close

The new disposal_complete check precedes the database-witness lookup. This is correct because the retained transaction's positive disposal observation records that its actual transaction was taken and dropped previously. The original vendor implementation requires the matching live/waiting database witness during that destruction, and never retries an entered disposal. Later closure does not revoke the already-completed destruction. This check does not invent a new witness, reopen the database, replay disposal or permit an uncertain transaction to disappear. The remaining errors stay inside the request until current outcomes are explicitly released.
