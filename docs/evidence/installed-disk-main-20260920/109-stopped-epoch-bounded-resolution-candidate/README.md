# Conditional stopped-epoch fixture resolution

Status: static candidate only; DO NOT APPLY before the unchanged run116 diagnostic establishes healthy leadership movement. This is not a production correctness fix. No actual Rust source was edited and no Rust build or test was run for this package.

Run109 returns the generic UnknownOutcome at service.rs441 after selecting a fresh leader. That condition combines term movement, loss of local leadership, and fatal running_state. The message alone cannot identify which condition occurred. Root installed the exact current/local/admitted-term diagnostic and is running the unchanged original assertion. A fatal storage or state-machine outcome needs its own production diagnosis; this candidate must not be substituted for it.

The stopped-epoch reducer returns an inner application Conflict with the exact message `control epoch permanently stopped` in lifecycle_state.rs125. Backend::apply serializes that inner result rather than propagating a fatal outer error. There is no successful receipt for this rejected new identity; absence alone therefore cannot prove rejection. The same signed command must reach a healthy current leader and return the actual rejection.

If run116 shows healthy role/term movement, this candidate allows exact-identity resolution within one outer five-second timeout after the same initial leader selection. It constructs the signed intent once and captures the original RequestContext once. Every subsequent call clones those same values; no new permanent identity, credential, or per-attempt overall deadline is created. The timeout covers all additional leader selection and attempts, including the Fixture::leader helper's internally longer timeout. UnknownOutcome/Unavailable never satisfies the test. A successful response fails the test. Conflict only satisfies the test with the exact stopped-epoch reason, so an unrelated admission-term Conflict cannot pass it.

Every attempted request is preceded and followed by checking all fixture groups through RaftGroup::check_access. That check includes snapshot custody, actual store access, core running_state, and machine_failed; a known core/storage failure fails immediately. An uncertain response is retried only if its executing member's observed term changed or it no longer names itself as leader. A stable-route failure fails immediately. These checks are diagnostics at observation time, not a claim to atomically prove the sole cause of a public sanitized error; the unchanged run116 cause remains a prerequisite for adopting this fixture strategy.

No production API, receipt persistence, reducer order, role fencing, storage failure handling, workload, or configured limit changes. All earlier replay/drain/receipt assertions remain. The assertion becomes stronger by requiring the actual stopped-epoch message. The original test's new-mutation service call already creates a five-second accepted-request deadline. This candidate applies one five-second outer bound to the whole resolution sequence; it does not use the existing twenty-second setup helper. Tokio deadlines retain their existing cooperative scheduling behavior and cannot preempt a synchronous storage call.

On timeout or other failure, the existing accepted_request owner continues to retain dispatched work. This candidate does not add a detached task, perform rollback, or interpret missing acknowledgement as missing effects. Normal successful resolution still reaches the fixture's existing close/drain.
