# Bounded lifecycle bootstrap vote observations

This is a fixture-only diagnostic proposal, not a production election correction. It changes tests/lifecycle.rs and adds its private common/bootstrap_vote_probe.rs module. It preserves the original100–180ms election settings,30ms heartbeat,100ms vote RPC TTLs,10s leader wait, all existing requests, contexts, assertions, and test bodies. No retry, fallback, election suppression, new authorization, deadline increase, or alternate bootstrap is introduced.

## What run124 establishes

Run124 is now terminal:12 tests passed and2 failed; process group40044 drained with inventoried source unchanged. Its first failure occurs at Fixture::open's initial leader wait, before current_control_administration_retains_exact_resource_revocation_and_original_lifetime performs any resource-revocation operation. Node1 is Candidate at term50 with the initial membership log0 and no applied entry. Nodes2/3 are Learners with no logs/membership, matching uncommitted persisted votes for node1 at term50, and running_state Ok. The frozen excerpt and complete terminal-log hashes are included. No live-log hash was treated as final.

Fixture::open creates all3 independent physical stores, registers every actual group/id route, and only then calls initialize_replicated on node1. bootstrap.rs validates the exact persisted bootstrap binding and designated voter. OpenRaft's initialization appends membership log0 locally and starts an election. The other nodes legitimately remain Learners until an elected leader replicates that membership. Engine::handle_vote_req can grant a sufficiently current request without local voter membership. Thus the observed empty learner memberships do not, by themselves, indicate malformed bootstrap, and their matching persisted votes show requests reached both peers.

The missing progress is an acknowledged current candidate quorum. core/raft_core.rs spawn_parallel_vote_requests gives each vote an election_timeout_min TTL (100ms here), and kasumi-raft Network::send applies that same RPC soft TTL around the actual router call. handle_vote_request enqueues its response after the vote handler's SaveVote command. SaveVote awaits the real LogStore::save_vote; Kasumi serializes it through io_gate and control_gate in spawn_blocking, calling the encrypted TenantStore write_batch. This is not a direct synchronous redb commit on the single Tokio worker, though storage scheduling/durable I/O can still delay the acknowledgement. The candidate ignores a delivered notification whose sender_vote no longer matches its candidate vote. About50 successive terms with no committed vote is consistent with repeated late/missing acknowledgement, but the final metrics alone do not distinguish timeout, grant rejection, delayed notification handling, or another cause. There is no proven production correction yet.

## Probe behavior and fixed bounds

BootstrapVoteProbe wraps the exact same InProcessRouter, which remains the object used by the fixture's network cuts and route registration. Append/snapshot requests and vote requests all go to the same router once, with the original group/source/target/node/request. The wrapper returns the same original Result unchanged. Only Vote requests add an observation; the cloned VoteRequest and successful VoteResponse contain only fixed scalar/LogId fields for u64 nodes. Successful response observations include the actual returned granted flag, vote term/node/committed bit, and last_log_id. A remote node's metrics are never substituted for that response.

History contains exactly32 inline optional entries and three metrics receiver slots. Each polled vote records its source, target, exact request, monotonic start offset, candidate published metrics at entry, and a terminal elapsed duration plus candidate published metrics at return/drop. Successful replies, remote Raft errors, transport errors and unexpected response variants are classified separately. Error text is a UTF-8-safe128-byte inline snapshot with an explicit truncation flag; the original full error object remains in the returned Result. There is no growing event Vec, detached observer, per-event logging, or hot-path printing. Full formatting occurs only inside the original leader-wait failure branch. Fixed inline scalar counters track starts, returns, drops, evictions and observations omitted while every slot is pending.

A slot is never replaced while its owning future is Pending. Terminal entries are reused in bounded circular order; evictions are explicit. If all32 slots remain pending, later traffic is still forwarded unchanged and the omission counter advances. The in-flight guard still contributes to return/drop totals but has no overwritten slot. No telemetry generation can update another active observation. Three watch receivers provide published scalar metrics without retaining Database or Raft handles; they are replaced on reopen and removed after each original shutdown completes. The router retains exactly its existing Raft registrations and is unregistered by the existing close loop.

A borrowed guard survives the actual inner await. If that polled future is dropped before a return, Drop records FutureDropped and whether the thread is currently unwinding. Completed observations set the guard finished synchronously before returning, so the guard cannot also classify a normal return as cancellation. No admission, persistence or runtime handle is consumed by this telemetry. No mutex or watch guard is held across await, and metrics sampling releases its guards before taking the history mutex. This instrumentation adds its small fixed storage and an ordinary async-trait forwarding layer; it is not a production memory-admission proof or a guarantee of zero observer overhead.

## Interpretation limits

The return sample is at the router-wrapper boundary, before Network adaptation and the candidate's Notify queue. Its candidate term is the latest published RaftMetrics value, which may lag private engine state. A same-term granted response at this boundary is not proof that the candidate processed it, counted it or remained in that term afterward. A FutureDropped observation proves only that this wrapper was first polled and later dropped without a returned result; it cannot identify which nested TTL or parent cancellation caused the drop, and it does not prove a dispatched remote operation stopped or rolled back. Futures dropped before their first poll are not observed. Error snapshots may truncate, older terminal entries may be evicted, and saturated history can omit identities, with each limit visible in the output.

These observations are intended to separate actual grant/term responses from100ms-scale wrapper drops, or identify replies whose published candidate term already changed. If they show timely same-term grants but no leadership, the next missing evidence is internal Notify handling/does_vote_match, not permission to accept the bootstrap failure. No original failure is classified away.
